# Unidot 开发意图与范围

记录日期：2026-10-09。以下是用户明确的产品方向，后续设计和实现应以此约束范围。

## 核心目标

> 关键是 Agent 可以实时编辑源代码，然后更新，玩家就能立刻看见变化。

Agent 编辑真实游戏源码，通过 Unidot 编译、更新并观察结果。衡量价值的是从源码修改到看到效果的迭代闭环，而不是工具功能的数量。

- 优先保证可靠的编译、部署、启动、诊断和结果反馈。
- 冷启动沿用现有 Unidot 流程；“一分钟内看到新效果”是迭代目标，完整耗时仍需实测。
- 2026-10-09 的初始目标环境为 Unity 2022.3.62f3、Windows x64、Mono；2026-10-10 用户将 MCP 目标扩展为 Unity 2022 Mono，见下方 Agent 入口约定。仍没有升级游戏 Unity 版本的需求。

## 避免过度开发

> 不要过度开发工具，尽管意图听起来非常好。

- 优先使用和完善已有能力，由真实使用中的阻碍决定新增功能。
- 不为追求通用热更新，提前改造大量游戏接口、DI 注册或生命周期。
- 暂缓通用代际程序集框架、任意类型替换和完整玩家状态迁移。它们不是当前 MCP 接入的前置条件。
- 不将本记录视为修改游戏源码、启动运行验证或发布版本的授权。

## 保留的后续想法

热更新可以以“加载新实现后，销毁并重新创建玩家”为生命周期边界，使游戏进程和世界继续运行。用户将此称为热启动。

这是候选方案，尚未实现或完成运行验收。重新创建玩家必须实际选择新实现；保存和恢复玩家状态按具体需要再做。

已有源码调查可供以后复用：

- `PlayerCharacterController` 位于 `Com.Project.B.CharacterController.Runtime`。
- 已找到的跨程序集运行时具体类型引用集中在 `PlayerFactory` 的 DI 注册；Editor 测试也有引用。
- 同一 Runtime 程序集中的 `CharacterStates` 和 `PlayerCameraController` 使用该具体类型，单独换掉控制器不能假定这些转换仍有效。
- `IPlayerCharacterController` / `ICharacterController` 位于独立契约程序集。
- 武器系统已有 Mod 重载回调；完整库存图状态迁移没有现成快照接口。

这些是导航结论，实施前应重新核对源码，不能据此声称任意玩家代码已经可热更新。

## 当前工作：Unidot MCP

回到 MCP 的最小可用闭环：连接 Unidot 所管理的 Player 会话，取得状态和诊断，通过外部执行器在 Unity 主线程执行代码，并返回结果或异常。

- 沿用外部 Mono bootstrap；0.8.0 起优先启动原游戏 EXE，再自动注入本次拥有的进程，保留游戏的路径/加载机制。该内部启动步骤不等于提供任意已有进程附加模式。
- 官方 `ModelContextProtocol.Core 2.2.0` 已通过最小 Mono 注入及 MCP 流传输验证，见 [验证记录](mcp-probe.md)。优先沿此路线接入，TouchSocket.Mcp 保留为备选；复用现有编译及会话生命周期。
- 先打通连接、执行和反馈，再由实际需求决定源码监听、玩家重建等后续能力。
- 运行实验必须明确请求、限时并安排停止清理；源码或文档检查不启动游戏。

### Agent 入口约定（2026-10-10）

- 正式 Agent 入口选择标准 MCP stdio：Agent 启动 Unidot MCP 子进程，由它启动、注入并管理 Unity Player。
- 用户不需要人工调试、先手动运行游戏或在运行后补充连接步骤；当前不开发已有进程附加模式。
- stdin/stdout 专用于 MCP 协议，日志使用 stderr 或文件；不需要第二个可见控制台窗口。
- Unidot 与 Player 之间优先复用已验证的会话专用命名管道，由 Unidot 内部管理，Agent 不处理管道名或端口。
- Agent 会话结束时清理所拥有的 Player 和通信资源。HTTP、端口选择及外部地址回调不属于当前入口的必要范围。
- 扩展目标为 Windows x64、Unity 2022 Mono；游戏默认后台启动，Development Build 不应作为注入前提。具体小版本是否验证成功应单独记录，不能承诺所有包。
- 0.7.0 开发版已实现正式 `unidot mcp` stdio 启动及编译/执行入口，并通过 RuntimeProbe 验收；使用方式见 [MCP 使用说明](mcp.md)。
